# Integration Guide

A CRS attestation record is a JSON document conforming to [`crs-v0.1-schema.json`](../crs-v0.1-schema.json). It is generated by an accredited independent auditor (F11 `attester_did`) after a calibration measurement period, cryptographically signed, and made available for query by regulators, counterparties, and risk systems.

## Attestation lifecycle

```
1. MEASURE     Deploying institution collects prediction/outcome pairs
               over the reporting period (minimum 90 days recommended).
               Computes CR (F5), FPR (F6), ECE (F7), human_review_rate (F8).

2. ATTEST      Independent auditor verifies the measurements.
               Auditor signs the 13-field record with their DID key (F11, F12).

3. REGISTER    Signed attestation record is published to a registry endpoint.
               Record is indexed by agent_did (F1).

4. QUERY       Counterparty agent or regulator queries the registry by agent_did.
               Registry returns the signed attestation record.
               Querying party computes compliance state from F5 and F7.

5. RE-ATTEST   Any trigger condition in F10 fires → new attestation
               cycle begins within the required window.
```

## Example attestation record

```json
{
  "agent_did": "did:web:agents.example-bank.com:trade-execution-v3",
  "reporting_period_start": "2026-07-01",
  "reporting_period_end": "2026-09-28",
  "system_scope": {
    "decision_categories": ["equity_trade_execution", "portfolio_rebalancing"],
    "deployer_did": "did:web:example-bank.com",
    "authorization_chain_reference": "sha256:a1b2c3d4e5f6..."
  },
  "calibration_rate": 0.87,
  "false_positive_rate": 0.04,
  "expected_calibration_error": 0.032,
  "human_review_rate": 0.005,
  "systematic_failure_disclosures": [],
  "reattestation_event_log": [],
  "attester_did": "did:web:crs-audit.accredited-firm.com",
  "attestation_date": "2026-09-30",
  "regulatory_jurisdiction": ["MAS", "HKMA"]
}
```

Compliance state for this record: **COMPLIANT** (CR = 0.87 >= 0.80; ECE = 0.032 < 0.05).

## Query pattern (HTTP)

```
GET /crs/v1/{agent_did}
Authorization: Bearer {token}

Response 200:
{
  "attestation": { ...13-field record... },
  "compliance_state": "COMPLIANT",
  "evaluated_at": "2026-10-16T08:00:00Z",
  "signature": "..."
}

Response 404:
{
  "error": "no_attestation_found",
  "agent_did": "did:web:..."
}
```

## Regulatory alignment

| Framework | CRS field | Alignment |
|---|---|---|
| US model risk governance gap (SR 26-2 explicitly excludes agentic AI) | F7 ECE, F10 re-attestation log | Addresses accountability gap for agentic AI systems not covered by existing US model-risk guidance |
| EU AI Act Art. 9 — risk management system | F5 CR, F7 ECE, F9 failures | Art. 9 requires an established, documented, and continuously maintained risk management system for high-risk AI |
| MAS FEAT — Fairness (Principles 1-4) | F5 CR, F8 human review rate | Fairness: justifiability and accuracy requirements for AIDA-driven decisions |
| ADGM FSRA — regulatory jurisdiction | F11 independent attester, F13 jurisdiction | Supported jurisdiction for deployments in the Abu Dhabi Global Market |

## DID infrastructure

Both `agent_did` (F1) and `deployer_did` (in F4) use W3C Decentralized Identifiers (DIDs). Any W3C DID method is supported. `did:web` is the recommended starting method for financial institutions — it maps DID resolution to a standard HTTPS endpoint under the institution's own domain.

DID specification: https://www.w3.org/TR/did-core/
