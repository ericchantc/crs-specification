A 13-field structured attestation protocol for autonomous AI agent calibration disclosure in regulated financial systems.

---

## The Problem

When an autonomous AI agent makes a consequential financial decision — approving a loan, executing a trade, flagging fraud — there is currently no standard format for recording that the agent was calibrated, by whom, and under whose authorisation.

Every major governance framework has acknowledged this gap:

- SR 26-2 (Fed/FDIC/OCC, April 2026) explicitly excluded agentic AI from its scope
- The FCA Mills Review (July 2026) called for enabling the foundations for agentic finance and identified accountability, identity, and authorisation as critical infrastructure gaps for AI agents operating in financial services
- MAS FEAT Principles (2018) established fairness, ethics, accountability and transparency requirements for AI in financial services but did not specify a standardised attestation format for agentic AI systems
- The EU AI Act (applicable August 2, 2026) requires automatic event logging for high-risk AI systems under Article 12 but does not specify what those records must contain

CRS is a proposed answer to that question.

---

## What CRS Defines

A CRS attestation record is a structured document generated by an accredited third-party auditor for a specific AI agent, covering a defined reporting period. It records 13 fields across three accountability dimensions:

### Attribution (Pillar 1)

| Field | Description |
|---|---|
| 1. `agent_did` | W3C DID uniquely identifying the AI agent |
| 2. `reporting_period_start` | Start of the calibration measurement period |
| 3. `reporting_period_end` | End of the calibration measurement period |
| 4. `system_scope` | Authorised decision categories, deployer DID, and authorisation chain reference |

### Disclosure (Pillar 2)

| Field | Threshold |
|---|---|
| 5. `calibration_rate` | Compliance: CR >= 0.80; remediation required: CR < 0.80 (30-day window) |
| 6. `false_positive_rate` | Recorded; no pass/fail threshold |
| 7. `expected_calibration_error` | Compliance: ECE < 0.05; remediation required: 0.05 <= ECE <= 0.10 (30-day); mandatory recalibration: ECE > 0.10 (72-hour) |
| 8. `human_review_rate` | Recorded; values < 0.001 trigger supervisory adequacy review; supports human oversight obligations under applicable AI governance frameworks |
| 9. `systematic_failure_disclosures` | Empty if no failures; populated with per-category CR/ECE values if failures occurred |
| 10. `reattestation_event_log` | Log of all material model updates triggering re-attestation |

### Governance (Pillar 3)

| Field | Description |
|---|---|
| 11. `attester_did` | W3C DID of the accredited third-party auditor |
| 12. `attestation_date` | Date the attestation was generated |
| 13. `regulatory_jurisdiction` | Jurisdiction(s) under which the attestation is issued |

Compliance determination (COMPLIANT / REQUIRES_REMEDIATION / MANDATORY_RECALIBRATION) is derived from fields 5 and 7 and not stored — it is computed at evaluation time.

## How It Connects to Insurance and Capital Treatment

A compliant CRS attestation is the evidentiary foundation for two consequential outcomes:

1. **Insurance eligibility** — AI agent liability insurers can reference CRS attestation status when underwriting policies. Agents without a current compliant attestation are ineligible for coverage. CRS is designed to be complementary with other AI certification standards addressing security and operational controls — calibration attestation and operational certification serve different but reinforcing assurance layers.

2. **Capital treatment** — CRS attestation status provides the standardized evidentiary record for supervisory review of model risk and capital adequacy at institutions deploying autonomous AI agents.

---

## Re-attestation Triggers

Five conditions require the deploying institution to obtain a new attestation:

- Standard (30-day window): prediction accuracy decline >= 5%, training data drift, deployment scope expansion, model architecture change
- Emergency (72-hour window): regulatory threshold breach (ECE > 0.10 during live operation)

---

## Relation to AIF

CRS implements the Disclosure component (Pillar 2) of the Accountability Infrastructure Framework (AIF). The full AIF also includes:

- **Pillar 1 — Attribution:** Agent identity via W3C DID/VC, re-attestation triggers, and hierarchical accountability chains.
- **Pillar 3 — Governance:** Consequence enforcement — insurance eligibility and capital treatment (fields 11-13 provide the evidentiary anchor).

## Contributing

Comments and feedback are welcome via GitHub Issues. See [CONTRIBUTING.md](CONTRIBUTING.md) for how to submit threshold reviews, implementation feedback, and schema issues.

If you are working on AI agent governance, insurance underwriting for AI, or regulatory compliance tooling and see gaps or implementation challenges in this design — open an issue. The threshold values (CR 0.80, ECE 0.05/0.10) are grounded in empirical calibration benchmarks from financial model validation literature and are explicitly open for review. The table below summarises the empirical basis:

| Paper | Domain | Finding | Relevance |
|---|---|---|---|
| Guo et al. (2017) ICML | Computer vision (foundational) | Temperature scaling brings ECE substantially below 0.05 post-calibration | Foundational empirical basis for the sub-5% ECE compliance threshold |
